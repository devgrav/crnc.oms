# Миграция SPA (`src/Client`) на современный стек

Тикет: [#9 Migrate SPA to modern stack](https://github.com/devgrav/crnc.oms/issues/9), milestone v0.9.0.

## Контекст

Бэкенд CRNC OMS полностью переведён на .NET 10 (четыре контекста, у каждого свой `.sln`, Dockerfile и e2e-набор на Testcontainers; см. `docs/migrations/*-net10-migration-plan.md`). SPA — последняя часть репозитория, оставшаяся на стеке 2018 года. Этот документ — план её миграции: он фиксирует принятые решения, порядок шагов и проверенные факты, на которые эти решения опираются.

Тикет #9 приносит свод правил из другого, более свежего React-проекта. Правила приняты как база, но **три пункта скорректированы** под реальность этого репозитория (§2.2, §4.1, §6.1) — с обоснованием в соответствующих разделах. Всё остальное принимается без изменений.

### Что есть сейчас (проверено чтением файлов)

`src/Client` — 3305 строк в 60 файлах (`src/**/*.ts*` + 1 CSS). Три экрана-сетки (orders, jobs, users), одна сложная модальная форма (order card), одна простая (user card), логин, layout с SignalR-колокольчиком.

| Зависимость | Версия в `package.json` | Состояние |
|---|---|---|
| react / react-dom | ^16.12.0 | актуальная ветка — 19.3.0 |
| typescript | ^3.7.4 | актуальная — 5.9.3 (и 7.0.2, см. §1.2) |
| webpack | ^3.10.0 | актуальная — 5.x; webpack 3 не собирается на Node > 16 (OpenSSL 3 убрал md4) |
| mobx / mobx-react | ^5.15.1 / ^6.1.4 | актуальные — 6.x / 9.x; но MobX предлагается убрать целиком, см. §3 |
| semantic-ui-react | ^0.88.2 | **тупик**, см. §2 |
| react-router-dom | ^5.1.2 | актуальная — 8.4.0 |
| axios | ^0.19.0 | актуальная — 1.20.0 |
| @microsoft/signalr | ^3.1.0 | актуальная — 10.0.11 |
| tslint | ^5.9.1 | deprecated с 2019, преемник — ESLint |
| babel-* (es2015, polyfill, regenerator) | 6.x | не нужны вообще |
| react-hot-loader | ^3.1.3 | заменяется штатным HMR Vite |
| guid-typescript, ts-simple-nameof | 1.x | удаляются, см. §7.3 |

Сборка прибита к `node:16-alpine` в `src/Client/Dockerfile` с развёрнутым комментарием, почему тег нельзя отпустить. После миграции этот комментарий и сам пин исчезают.

### Почему не инкрементальный апгрейд

Обновить можно только весь стек разом: webpack 3 → 5, TS 3.7 → 5.9, React 16 → 19, MobX-декораторы → хуки, Semantic UI → другой кит, tslint → ESLint. Ни один из этих шагов не изолирован — `@observer`-классы не переживают выкидывание декораторов, `React.SFC` и `componentWillReceiveProps` удалены из типов React 18+, Semantic UI не дойдёт до React 19 в принципе (§2.1). После такого прохода нетронутым не остаётся ни одного файла, кроме картинок и `Paging.css`.

Поэтому: **переписывание `src/Client` на месте, экран за экраном, в одной ветке**, со старым кодом в истории git. Каркас (§1) ставится первым коммитом поверх удалённого webpack-конфига; дальше экраны переносятся по одному, каждый — отдельным коммитом, зелёным по `tsc -b` и линту. Промежуточные коммиты не обязаны давать рабочее приложение целиком, но ветка не мержится в `master`, пока Playwright-набор (§0) не станет зелёным на новом фронте.

## §0. Пререквизит: Playwright-тесты против **текущего** SPA

Тикет (п. 4) предлагает сначала собрать Playwright, потом Vitest. Принимается, и это же — устоявшаяся практика репозитория: все четыре .NET-миграции начинались с фиксации baseline e2e-тестами на старом коде.

Новый проект: `src/Client/e2e/` (Playwright, TypeScript), запуск — `npx playwright test`, окружение — `docker-compose --profile client up` (сиды известны: `admin/111111`, `shon_bean/111111`).

Минимальный набор сценариев, покрывающий все роли и оба типа форм:

1. `login` — неверный пароль → сообщение об ошибке; верный → редирект на `/orders`.
2. `orders-grid` — список заказов виден менеджеру; число строк > 0.
3. `order-create` — «Add order» → заполнить обязательные поля → Save → заказ появился в сетке.
4. `order-validation` — Save с пустым Job Description → 400 → подсветка поля и сообщение в шапке модалки (регрессия на формат ошибок, §2.3).
5. `order-edit` — открыть существующий, сменить статус, Save, убедиться, что значение сохранилось.
6. `jobs-grid` — сетка jobs открывается у менеджера.
7. `users-crud` — под `admin`: создать пользователя, найти поиском, деактивировать, удалить.
8. `forbidden` — `shon_bean` на `/users` → экран Forbidden (не 404, не белый экран).
9. `not-found` — `/nonexistent` → NotFound.
10. `push-notification` — под `admin` перевести заказ `shon_bean` в статус, порождающий уведомление; во второй сессии (`shon_bean`) дождаться бейджа на колокольчике. Сценарий самый хрупкий — если окажется нестабильным, помечается `test.fixme` и переносится в §8, но писать его нужно **до** миграции: сейчас это единственное доказательство того, что SignalR-канал вообще работает.

Селекторы: только `data-testid`, проставленные в старом коде и перенесённые в новый. Тексты Semantic UI при смене кита изменятся — на них опираться нельзя.

Baseline фиксируется в `master` отдельным PR, до начала §1.

### Выполнено

Набор написан и зелёный на текущем приложении: **18 тестов, два прогона подряд** (второй — на уже загрязнённой предыдущим прогоном базе, чтобы поймать зависимость тестов друг от друга), `tsc --noEmit` чистый. Проект — `src/Client/e2e`, команды и конвенции описаны в его `README.md` и в AGENTS.md.

| Спека | Тестов | Что покрывает |
|---|---|---|
| `login.spec.ts` | 4 | вход, ошибка пароля, выход, редирект неаутентифицированного |
| `orders.spec.ts` | 4 | сетка, создание, валидация, смена статуса |
| `users.spec.ts` | 4 | создание, валидация, удаление, поиск |
| `access.spec.ts` | 4 | Forbidden менеджеру, доступ админа, обход гарда админом, NotFound |
| `jobs.spec.ts` | 1 | сетка jobs |
| `push.spec.ts` | 1 | две сессии, цепочка Sales → шина → Gateway → Push → SignalR → бейдж |

Решения, которые пришлось принять по ходу и которые важны для §1 и §9:

- **Отдельный `package.json` у `e2e/`.** Образ SPA собирается на `node:16-alpine` и выполняет `yarn`, то есть ставит и devDependencies; Playwright требует Node 18+ и на postinstall тянет браузеры. Попади он в манифест `src/Client` — сломал бы сборку образа. `e2e/` вдобавок добавлен в `.dockerignore`. После §1 (Vite, Node 22) объединение станет возможным, но не обязательным.
- **В `.dockerignore` добавлен `node_modules`.** Там была только строка `.node_modules` — с точкой, то есть не исключавшая ничего: локальные модули могли попасть в контекст и затереть контейнерные через `COPY . .`. Латентный баг сборки, не связанный с тестами.
- **Semantic UI кладёт `data-testid` в разные места**: у `Form.Input` — на обёртку `div.ui.input`, у `Form.TextArea` — прямо на `<textarea>`, у `Form.Select` — на корень Dropdown (опции внутри него доступны как `role="option"`). Из-за этого в наборе есть `support/form.ts` с `fillField`/`selectOption`. После перехода на Mantine эта прослойка схлопнется до обычных `fill`/`selectOption` — но сами testid'ы переносятся один в один.
- **`RoleSelect` перечисляет свои пропсы явно** и ничего не спредит, поэтому `data-testid` до DOM не доходил — компоненту добавлен проп `testId`. Это единственная правка старого кода, выходящая за пределы «добавить атрибут».
- **`workers: 1`, `fullyParallel: false`** — одна общая база на стенде, а сетки считают строки. Данные тестов уникальны (`unique()`), но детерминированность baseline важнее скорости: весь набор идёт ~40 секунд.
- **`E2E_BROWSER_CHANNEL`** — переключатель на системный Chrome для машин, где скачивание браузеров Playwright заблокировано. CI работает на штатном бандле.

Баги текущего приложения, найденные тестами (оба перечислены в §6.2 и §6.3 и чинятся при переносе соответствующих экранов): фиктивная пагинация в сетке заказов подтвердилась, у пользователей — сломанный поиск и недостижимая без поиска новая карточка.

## §1. Каркас

### 1.1. Сборка

Vite 8 + React 19.3 + `@vitejs/plugin-react` 6, ESM (`"type": "module"`), скрипты:

```
npm run dev        # vite
npm run build      # tsc -b && vite build
npm run preview    # vite preview
npm run lint       # eslint .
npm run test       # vitest run
npm run e2e        # playwright test
```

`tsc -b` в `build` — обязательно (правило 2 тикета): типы должны ломать сборку, а не только подсвечиваться в IDE. Vite 8 требует Node `^20.19 || >=22.12`; локально стоит Node 22.13.1, в Dockerfile — `node:22-alpine` (фиксированный мажор, без плавающего `node:alpine`: причина пина остаётся прежней, меняется только версия).

### 1.2. TypeScript: 5.9.3, не 7.0.2

TypeScript 7 (нативный порт) уже `latest` на npm, но `typescript-eslint@8.70.1` — включая `canary` — объявляет peer `typescript: >=4.8.4 <6.1.0`. Правило 3 тикета требует `recommendedTypeChecked`, то есть линтер с типами обязателен. Значит **TS 5.9.3**, а переход на 7.x — отдельная задача после того, как typescript-eslint его поддержит.

`tsconfig.json` (правило 6): `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `verbatimModuleSyntax`, `moduleResolution: "bundler"`, `jsx: "react-jsx"`, алиас `@/* → src/*` (дублируется в `vite.config.ts` через `resolve.alias`).

### 1.3. Линт

ESLint 10 flat config (`eslint.config.js`): `typescript-eslint` recommendedTypeChecked, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`, `no-console: error` (правило 36 — сейчас `console.log` есть в `config.ts`, `Notifications.tsx`, `ValidationInfo.ts`). `tslint.json` и `.babelrc` удаляются.

### 1.4. Структура (правило 13)

```
src/
  components/        общие компоненты и layout
  pages/<фича>/      страница + её собственные компоненты + __tests__/
  hooks/
  services/          транспорт и операции API
  types/             *.types.ts контрактов
  auth/
```

Один компонент — один файл, PascalCase, `export default`, без barrel-файлов (правило 10). Текущая раскладка `components/<feature>/<subfeature>/` близка к целевой — меняется в основном то, что «страница» переезжает в `pages/`, а `*Container`/`*RootStore`/`*Store` исчезают (§3).

## §2. Библиотека компонентов

### 2.1. Semantic UI React — тупик, это решение, а не предпочтение

Проверено на npm 2026-09-22:

- `semantic-ui-react@latest` = **2.1.5**, опубликована три года назад; `time.modified` — 2023-12-30.
- peer-диапазон latest: `react: ^16.8.0 || ^17.0.0 || ^18.0.0` — **React 19 в него не входит**.
- v3 существует только как `3.0.0-beta.2` в теге `beta`; стабильного релиза нет.
- Причина не косметическая: до v3 кит держится на `ReactDOM.findDOMNode`, который React 19 удалил. Затронуты ровно те компоненты, на которых стоит весь этот SPA — `Modal`, `Popup`, `Dropdown`/`Select`, `Transition`, `Dimmer`.

Вывод: связка «React 19 + semantic-ui-react» нерабочая и не станет рабочей. Остаться на React 18 ради кита — значит сознательно мигрировать на предыдущую мажорную версию. Кит меняется.

### 2.2. Чем заменить

| Кандидат | Версия / peer react | За | Против |
|---|---|---|---|
| **Mantine 9** | 9.6.2 / `^19.2.0` | родной React 19; философия близка к Semantic UI (компоненты + хуки, без навязанного design language); TS-first; стили на CSS-модулях с переменными, без рантайм-CSS-in-JS; style props вместо самописного CSS | в базовом `Table` нет сортировки/пагинации «из коробки» — либо руками, либо `mantine-react-table` |
| Ant Design 6 | 6.6.5 / `>=18` | `Table` с пагинацией, сортировкой и фильтрами «из коробки» — ровно то, что нужно трём сеткам; огромный набор для админок | тяжёлый и очень опинионированный; свой стиль форм; заметно больший бандл |
| MUI 9 | 9.4.0 / `^17 \|\| ^18 \|\| ^19` | самая крупная и самая старая живая экосистема — наименьший риск повторить историю Semantic UI; `@mui/x-data-grid` 9.14.0 под **MIT** закрывает сортировку, фильтрацию и пагинацию, то есть снимает минус Mantine | Material-вид как узнаваемый дизайн-язык; требует Emotion (рантайм CSS-in-JS) либо экспериментальный `@mui/material-pigment-css`; более многословная API |
| shadcn/ui + Tailwind | — | полный контроль, минимальный рантайм | всё пишется руками — для этой задачи максимум работы при минимуме выгоды |

**Решение: Mantine 9** — но выбор близкий, и два расхожих аргумента в этом сравнении не работают, поэтому зафиксированы явно:

- **«У MUI платный грид» — неверно.** `@mui/x-data-grid` 9.14.0 лицензирован MIT и покрывает сортировку, фильтрацию и пагинацию; Pro нужен для tree data, группировки строк и пиннинга колонок — ничего из этого в трёх сетках нет.
- **«У Mantine есть `@mantine/form`» — не аргумент здесь.** По правилу 24 тикета формы живут на локальном `useState`, так что форм-пакет кита не используется ни в одном из вариантов.

Что осталось после вычитания этих двух пунктов: MUI выигрывает по долговечности (и это прямой урок текущей миграции — кит умер), Mantine — по нейтральности внешнего вида (приложение не станет выглядеть Material-админкой) и по отсутствию рантайм-CSS-in-JS. Оба объявляют React 19 в peer. Берём Mantine, потому что задача — обновить стек, а не сменить дизайн-язык; **если приоритетом станет максимальная страховка от повторной смерти кита, правильный ответ — MUI 9, и это осознанная развилка, а не недосмотр.**

Правило 31 тикета («готовый UI-кит + его утилитарные классы») выполняется style props Mantine; правило 32 (адаптивность брейкпоинтами кита) — его `visibleFrom`/`hiddenFrom` и `useMediaQuery`.

Ant Design остаётся запасным вариантом, и единственный аргумент, способный его вернуть, — если ручная пагинация/сортировка в трёх сетках окажется дороже, чем кажется. Оценить это можно после §6.1 (первая сетка), не раньше.

`semantic-ui-css` (≈600 КБ CSS, импортируется целиком в `app.tsx`) удаляется вместе с китом.

### 2.3. Что ломается вместе с китом

`Form.Input`/`Form.Select` Semantic UI передают в `onChange` пару `(event, data)`, и на этом построены **все** формы: `onChange(event, data)` читает `data.name` / `data.value` / `data.checked`. У Mantine контролы отдают либо событие, либо сразу значение. Значит все обработчики форм переписываются — но переписывать их и так пришлось бы под правило 26 тикета (единый props-контракт `label / value / onChange / error / isLoading / disabled`).

Заодно исчезает `ts-simple-nameof`: `nameof<BaseOrderModel>(x => x.jobType)` нужен был, чтобы связать строковое `name` контрола с полем модели. В типизированном `useState`-состоянии формы ключ — обычный строковый литерал, проверяемый компилятором.

## §3. Состояние: MobX убирается, Redux не добавляется

Это прямой ответ на вопрос из постановки задачи, и он подкреплён тем, что в коде уже есть.

### 3.1. Сегодняшние сторы не глобальные и не реактивные по существу

`OrdersGridContainer` создаёт `new OrdersGridRootStore()` в поле экземпляра — то есть **при каждом монтировании**; то же у `OrderCardContainer` и `JobsGridContainer`. Ни один стор не переживает переход между роутами, ни один не шарится между экранами. Это уже локальное состояние, просто обёрнутое в `Provider` + `@inject` + `@observer`.

Содержимое типичного стора (`OrdersGridStore`, 53 строки): поле `model`, поле `isLoading`, методы `showLoading`/`hideLoading`, метод `getOrders`, который вызывает `OrderService.getOrders()` в try/finally, и `setModel`. Плюс `OrdersGridRootStore` (13 строк), который не делает ничего, кроме конструирования первого, и `OrdersRootStores` — интерфейс-словарь для `@inject`. Три файла и `Provider`-обёртка ради одного запроса к API.

При этом сами по себе стор-классы не являются антипаттерном — но здесь они не дают ничего, чего не даёт хук: нет общего состояния, нет подписок между сторами, нет вычислений поверх нескольких источников. `@computed`-геттеры в `OrderCardRootStore`/`EditOrderCardStore` делают ровно одно — приписывают элемент `{value: 0, text: "Not chosen"}` в начало списка опций.

### 3.2. Целевая модель

- **Серверные данные** (списки заказов, карточка заказа, пользователи, роли, jobs) — `@tanstack/react-query` 5.103.2. Загрузка, `isLoading`, кэш, инвалидация после мутаций, отмена при размонтировании — всё то, что сейчас разложено руками по сторам. После сохранения заказа `invalidateQueries(['orders'])` заменяет нынешнюю ручную перезагрузку (`UserCards.handleSave` → `getUsers()` → два `setState`).
- **Формы** — локальный `useState` (правило 24). Никакого глобального состояния ради полей ввода.
- **Текущий пользователь** — один React Context (`AuthProvider`) с `user | null`, `signIn`, `signOut`; восстановление из `sessionStorage` при инициализации состояния. Это единственное по-настоящему общее на всё приложение состояние.
- **Push-уведомления** — свой Context поверх SignalR-подключения (§8), потому что подключение должно быть одно на приложение, а показывать уведомления в перспективе может не только колокольчик.
- **Глобальный стор не заводится** (правило 29). Redux/Zustand/Jotai здесь нечего хранить: после выноса серверных данных в React Query и текущего пользователя в Context глобального клиентского состояния в приложении не остаётся. Если оно появится позже — вводить точечно, под конкретную задачу, а не «на вырост».

### 3.3. Что уходит

Удаляются: `mobx`, `mobx-react`, все `*RootStore.ts`, `*Store.ts`, `*RootStores.ts`, `*Container.tsx`, `ValidationInfo.ts`, `experimentalDecorators` в tsconfig. Контейнеры по правилу 11 тикета остаются как понятие («контейнер держит состояние и вызывает сервисы, presentational получает всё через props»), но контейнер — это теперь компонент страницы с хуками, а не фабрика сторов с `Provider`.

## §4. Транспорт и ошибки

### 4.1. Четыре бэкенда и правило «относительный baseURL»

Правило 20 тикета («baseURL относительный, хост бэкенда не хардкодится») написано для проекта с одним бэкендом. Здесь их четыре: Security (8090), Sales (8091), Production (8098), Push-хаб (8107) — плюс `config.ts`, который читает URL'ы из `process.env.REACT_APP_*`, запечённых в бандл как Docker build args (`docker-compose.yml`, сервис `crnc-oms-ui`). Из-за этого адрес каждого сервиса зашит в образ на этапе сборки, и каждый вызов — кросс-оригинный, из-за чего все четыре сервиса держат `AddCors`.

**Решение: reverse-proxy в самом nginx SPA-контейнера.** Контейнер с фронтом уже есть, свой `conf/conf.d/default.conf` уже есть — добавляются location'ы:

```
/api/security/  → http://security-api:8080/api/
/api/sales/     → http://sales-api:8080/api/
/api/production/→ http://production-api:8080/api/
/hubs/push      → http://notification-push-api:8080/hubs/push
```

В dev то же самое делает `server.proxy` в `vite.config.ts`, указывая на `localhost:8090/8091/8098/8107`. В обоих режимах фронт видит один origin и относительные пути — правило 20 выполняется буквально, `config.ts` с его `throw` при старте и четырьмя `console.log` исчезает, build args из `docker-compose.yml` уходят, CORS на бэкенде становится ненужным (конфиги не трогаем — они не мешают и полезны при прямом обращении к сервисам).

Два подводных камня, которые нужно учесть сразу:

- **WebSocket.** Для `/hubs/push` обязательны `proxy_http_version 1.1`, `proxy_set_header Upgrade $http_upgrade`, `proxy_set_header Connection $connection_upgrade` и `map $http_upgrade $connection_upgrade { default upgrade; '' close; }`. `map` живёт в http-контексте, а файлы из `conf/conf.d/` подключаются именно туда, так что объявить его можно рядом. Без этого SignalR не упадёт — он молча откатится на long polling, и заметить это можно будет только по вкладке Network.
- **Резолвинг имён.** nginx резолвит `proxy_pass http://security-api:8080` один раз при загрузке конфига и кэширует IP навсегда. Если бэкенд пересоздадут, прокси начнёт стучаться в мёртвый адрес. Лечится штатно: `resolver 127.0.0.11 valid=10s;` плюс `proxy_pass` через переменную (`set $upstream http://security-api:8080; proxy_pass $upstream/api/;`).

Запасной вариант, если прокси по какой-то причине не подойдёт: рантайм-конфиг — `envsubst` на старте контейнера генерирует `/config.js`, `index.html` его подключает. Это решает только запекание URL в бандл и не решает CORS; берём только если §4.1 провалится на практике.

### 4.2. Клиент и сервисы

`services/apiClient.ts` — один настроенный `axios` (baseURL `/api`, timeout, request-интерцептор, подставляющий `Authorization: Bearer` из текущего токена). Это чинит сегодняшний `AxiosProxy`: он кладёт токен в `defaults.headers.common` **в момент создания** инстанса и поэтому требует ручного `AxiosProxy.clear()` при каждой смене пользователя — интерцептор читает токен на каждом запросе и ломаться так не умеет.

Сервисы (`orders.service.ts`, `users.service.ts`, …) — операции поверх клиента. Наружу исключения не бросают, возвращают `{ success, data?, fieldErrors?, generalError? }` (правила 19, 21). Хуки React Query вызывают сервисы; компоненты не знают ни про axios, ни про URL.

### 4.3. Нормализация ошибок — три формата, а не один

Правило 22 требует один error-handler. Он обязан покрывать **три реально существующих в этом бэкенде формата** 400-х:

1. **`ValidationProblemDetails`** — `{ type, title, status, errors: { jobType: ["..."] } }`. Отдают контроллеры с `[ApiController]`: `Crnc.Oms.Sales.WebApi/Controllers/OrdersController.cs:22`. Сегодняшний фронт разбирает это в `OrderCardRootStore.setValidationInfo` (читает `validationInfo.errors`).
2. **Плоский `SerializableError`** — `{ firstName: ["..."] }`, без обёртки `errors`. Отдаёт `Crnc.Oms.Security.WebApi/Controllers/UsersController.cs:141,185` — там `BadRequest(ModelState)` при **отсутствующем** `[ApiController]` (строки 20–30 файла). Сегодняшний фронт разбирает это отдельным кодом в `UserCardEdit.onSave`, который читает `error.response.data` как словарь напрямую.
3. **Голая строка** — `BadRequest("Not valid login or password")` в `Crnc.Oms.Security.WebApi/Controllers/AccountsController.cs:61,65,68`. `Login.tsx` показывает `error.response.data` как текст.

Плюс сетевой сбой и 5xx. Плюс — отдельным пунктом из правила 22 — ошибка внутри бинарного ответа: сейчас скачивания файлов в SPA нет, но фото пользователя уже ездит как base64 в JSON, и если появится нормальная выгрузка, дыра будет ровно там.

Ключи `fieldErrors` (правило 23) совпадают с именами полей формы: бэкенд гарантированно отдаёт их в camelCase — и в Sales, и в Security это `DictionaryKeyPolicy = JsonNamingPolicy.CamelCase` в `Program.cs`, причём в Security на это есть регрессионный e2e-тест `CreateUser_MissingRequiredField_ReturnsBadRequestWithCamelCaseKeys`. Контракт зафиксирован с обеих сторон — при переименовании полей формы его надо держать.

Хук `useFormValidation` (правило 25): `errors`, `generalError`, `getErrorMessages(field)`, `clearAllErrors()` и обёртка сеттера, гасящая ошибку поля при первом вводе. Сейчас эта логика существует **дважды** — как MobX-класс `ValidationInfo` (61 строка, `tryRemoveFieldValidationInfo`) и как ручной `setState`-код в `UserCardEdit.onChange` (строки 96–116 файла). После миграции — один хук.

### 4.4. Типы контрактов

Хэндвритten `*.types.ts` в `src/types/` (правило 8). Сейчас DTO разбросаны по коду и уже разъехались с бэкендом: интерфейс `CurrentUser` (`src/auth/CurrentUser.ts`) объявляет `login / fullName / role / jwt`, а `CurrentUserDto` в `AccountsController` отдаёт ещё и `Id`.

Отдельным шагом **после** стабилизации стоит рассмотреть генерацию типов из OpenAPI: все шесть WebApi держат `NSwag.AspNetCore 14.7.1`, то есть схемы уже публикуются. `openapi-typescript` + скрипт `npm run api:types` против поднятого `docker-compose`, результат коммитится. Это убирает дрейф вроде описанного выше. Не блокер миграции и не входит в её объём.

## §5. Роутинг и аутентификация

### 5.1. react-router 8, а не 7

Тикет (правило 15) называет v7; на момент написания плана `latest` — **8.4.0** с peer `react: >=19.2.7`, а v7 живёт в теге `version-7` (7.18.4). Поскольку каркас всё равно на React 19.3 и это гринфилд, берём 8.4.0: декларативный режим и API маршрутов между 7 и 8 совпадают, а начинать миграцию с предпоследней мажорной версии смысла нет. Если всплывёт несовместимость с китом или тестами — откат на 7.18.4 дешёвый и локальный.

### 5.2. Карта маршрутов

Вся карта — в одном месте (правило 15), layout-route с `<Outlet/>` вместо `<Layout>`-обёртки в каждом `PrivateRoute` (правило 16), `index`-редирект и catch-all `path="*"` → NotFound (правило 17). Тяжёлые маршруты — `React.lazy` + `Suspense` (правило 18); кандидат ровно один — карточка заказа со всеми её подформами.

Карточка заказа сейчас — модалка, отрисованная на роуте `/orders/:id` поверх пустого фона. Паттерн сохраняем, но делаем его явным: `/orders` — layout со списком, `/orders/:id` и `/orders/new` — дочерние роуты, рендерящие модалку поверх списка. Это заодно чинит нынешнее поведение, когда за открытой карточкой сетки не видно.

### 5.3. Гард

Сейчас в `routes.tsx` роль проверяет `PrivateRoute`, и там есть неочевидное правило: `Admin` проходит **на любой** роут независимо от объявленного `roles`. Поведение не случайное (админ должен видеть всё) — переносим его как есть, но явным `if` с комментарием, а не условием в тернарнике на 4 строки.

`CurrentUserContext` — статический синглтон, который мутируется вне React (`CurrentUserContext.init(user)`), из-за чего смена пользователя не вызывает перерисовку; сегодня это замаскировано редиректом после логина. Заменяется настоящим Context + `useAuth()`. Побочно уходит `(window as any).currentUserContext = CurrentUserContext` из `init` — отладочный хвост, отдающий JWT в глобальную область.

Хранилище токена остаётся `sessionStorage` под тем же ключом `crnc.oms.currentUser`: смена схемы хранения — отдельный разговор про безопасность, в объём миграции не входит.

## §6. Перенос экранов

Порядок — от самого простого к самому сложному, чтобы каркас (§1–§5) успел устояться на дешёвых экранах.

### 6.1. Jobs (самый простой: одна сетка, только чтение)

`JobsGridContainer` + `JobsGridRootStore` + `JobsGridStore` + `JobsGrid` + `JobsGridRow` → `pages/jobs/JobsPage.tsx` + `JobsTable.tsx` + `useJobs()` (React Query). На этом экране проверяются все решения разом: кит, клиент, нормализатор ошибок, лэйаут.

### 6.2. Orders grid

То же самое, плюс: **пагинация в сетке заказов сейчас фиктивная** — футер `OrdersGrid.tsx` рисует хардкодные ссылки «1 2 3 4» без обработчиков, а `OrderService.getOrders()` забирает `response.data.items` целиком. При переносе либо делаем клиентскую пагинацию компонентом кита (как в `UserCards`, где `Paging` настоящий), либо честно убираем футер. Серверную пагинацию не вводим — это изменение API и предмет отдельного тикета.

### 6.3. Users

Самый большой файл проекта (`UserCards.tsx`, 327 строк) плюс `UserCardEdit.tsx` (277). Здесь же уходит `componentWillReceiveProps` (удалён из React 18+) — его работа («вытащить редактируемого пользователя из параметра роута») становится `useParams()` + производным значением.

Клиентские поиск и пагинация по загруженному списку сохраняются как есть — это осознанное поведение экрана, а не недоделка. Но два дефекта, найденные e2e-набором (§0), при переносе чинятся:

- **Поиск не работает без выбранной роли.** В `UserCards.handleSearch` стоит `if (this.state.search.role)`, а начальное значение — `Guid.EMPTY`, то есть строка из нулей, которая истинна. В результате фильтр всегда доходит до `u.roleId === Guid.EMPTY` и отдаёт пустой список: поиск по одному логину или имени сегодня не возвращает ничего. В новом коде состояние поиска хранит `roleId?: string` с `undefined` по умолчанию, и проверка становится честной.
- **До созданного пользователя не добраться без поиска.** Сетка режет по 8 карточек, новый пользователь оказывается на последней странице, а после сохранения список перезагружается с `activePage = 1`. Нужно либо переводить на страницу с новой карточкой, либо сортировать по дате создания — решается при переносе, но решение должно быть явным.

Оба поведения зафиксированы в e2e-наборе комментариями и обойдены (тест ищет карточку поиском с ролью), а не закреплены как правильные: после починки тесты упростятся.

### 6.4. Order card — самый сложный

`OrderCard` + `OrderInfo` + `CustomerInfo` + `ContactPersonInfo` + `NewOrderCard` + `EditOrderCard` + `BaseOrderModel`/`NewOrderModel`/`EditOrderModel` + два стора. Правило 12 тикета («дублирующиеся формы сводятся к одному компоненту с props-конфигом») ложится сюда идеально: `NewOrderCard` и `EditOrderCard` — это одна форма, отличающаяся набором видимых полей (`isEdit` уже гоняется пропом через всю иерархию) и вызываемым сервисом.

Здесь же чинится `EditOrderCardStore.editOrder`: сейчас он ловит ошибку, разбирает только `status === 400`, а **любую другую проглатывает молча** — пользователь видит, как гаснет лоадер, и ничего больше. Нормализатор из §4.3 убирает эту ветку по построению.

### 6.5. Login, Layout, NotFound, Forbidden

Мелочь, но в `Login.tsx` есть мёртвый код, который не надо тащить: `withRouter(Login)` вызывается на верхнем уровне модуля и результат выбрасывается (строка 114), импортируется `string` из `prop-types`. В `app.tsx` не используются импорты `Layout`, `Header`, `Container`; в `index.tsx` — `Router`. В `routes.tsx` — `;;`.

## §7. Надёжность и чистка

### 7.1. Обязательное (правила 34–36)

- `<StrictMode>` включён. С Semantic UI это было невозможно (`findDOMNode` в StrictMode сыпал предупреждениями и падениями) — ещё одна причина смены кита.
- Корневой `ErrorBoundary`: сегодня упавший компонент даёт белый экран, а `CurrentUserContext.user` бросает `Error("Current user is not defined")` при любом обращении без логина — т.е. белый экран достижим штатным путём.
- `no-console` в ESLint.

### 7.2. Язык интерфейса

Правило 33 требует осознанного решения. UI целиком на английском (кнопки, заголовки, сообщения), README и комментарии — на русском. Решение: **один язык, английский, хардкод; i18n не вводится**. Зафиксировать в AGENTS.md (§10).

### 7.3. Удаляемые зависимости

`guid-typescript` используется ради `Guid.EMPTY`, `Guid.parse`, `Guid.isGuid` — заменяется константой `EMPTY_GUID` и одной regex-проверкой. `ts-simple-nameof` — см. §2.3. Плюс всё из таблицы §0: webpack 3 и его лоадеры, babel-*, react-hot-loader, tslint и три его плагина, `@types/*` для react 16, `typings/importFiles.d.ts` (Vite объявляет модули статики сам через `vite/client`).

`@microsoft/signalr` 3.1 → 10.0.11. Серверная часть — `app.MapHub<PushHub>("/hubs/push")` в `Crnc.Oms.Notification.Push.WebApi/Program.cs:127`, метод клиента `ReceivePushMessageAsync(string userId, string message)` (`IPushNotificationClient.cs:9`), адресация — `Clients.User(...)`, то есть по claim `nameid` из JWT. ## §9. Docker, compose, CI

### 9.1. Образ

`conf/conf.d/default.conf` — добавляются location'ы прокси; `gzip.conf` остаётся как есть.

### 9.2. Версия приложения (правила 41–42)

Версия берётся из одного источника — `package.json` пробрасывается в бандл через `define` в `vite.config.ts`, в UI показывается из сборочного артефакта. SPA-fallback на `index.html` уже настроен (`try_files $uri $uri/ /index.html`), ничего делать не нужно.

### 9.3. CI

Сейчас пайплайн один — `backend-ci.yml`, и он явно backend-only, с path-фильтром по контекстам под `src/Server/src/Crnc.Oms.<Context>/`. Клиент в него не вписывается: другая экосистема, другой кэш, другие артефакты. Добавляется **отдельный** `.github/workflows/client-ci.yml`, по тем же принципам, что описаны в `docs/ci/backend-ci.md`:

- триггеры: push в `master`, PR, `workflow_dispatch`; path-фильтр `src/Client/**` + сам workflow;
- джоба `build`: `npm ci` → `npm run lint` → `tsc -b` → `vitest run` → `vite build`, кэш npm через `actions/setup-node`;
- джоба `e2e`: поднимает `docker compose --profile client up -d`, ждёт готовности, гоняет Playwright, складывает HTML-отчёт и трейсы в артефакты вне зависимости от результата;
- сводная джоба `client-ci`, которая и ставится в branch protection (skipped = зелёный), — ровно по той же причине, что `backend-ci` в бэкендовом пайплайне;
- только first-party actions (`checkout`, `setup-node`, `cache`, `upload-artifact`);
- `DOCKER_HOST` не задаётся — на Linux-раннере он не нужен, как и в backend-ci.

Документация пайплайна — `docs/ci/client-ci.md`, парная к существующей `backend-ci.md`.

README (русский) содержит скриншоты интерфейса Semantic UI — после смены кита они устареют; переснять в конце.

## Риски

1. **Внешний вид меняется полностью.** Смена кита — это не рефакторинг, а редизайн; сравнивать «было/стало» попиксельно бессмысленно. Единственная защита от функциональных регрессий — Playwright-набор из §0, и именно поэтому он пишется до миграции и на `data-testid`.
2. **SignalR за прокси молча деградирует.** Без `Upgrade`/`Connection` в nginx подключение не падает, а уходит в long polling. Проверяется вкладкой Network (`/hubs/push?id=...` без 101 Switching Protocols) и тестом #10.
3. **Три формата ошибок валидации (§4.3).** Самое вероятное место тихой поломки: подсветка полей перестанет работать на одном из двух бэкендов, а сообщение в шапке останется. Покрывается unit-тестами нормализатора и Playwright-тестом #4.
4. **Mantine `Table` без встроенной пагинации.** Если ручная реализация в трёх сетках окажется дороже ожидаемого — переоценить выбор кита после §6.1, пока перенесён один экран (§2.2).
5. **TypeScript 7 подождёт.** Соблазн взять `latest` есть, но `typescript-eslint` его не поддерживает, а типизированный линт — требование тикета (§1.2).
6. **Объём.** Переписывается весь фронт; ветка будет жить долго. Смягчение — коммит на экран, `master` не блокируется (бэкенд в ветку не входит), мерж только после зелёного Playwright.

## Что в объём не входит

Серверная пагинация и серверный поиск; изменение контрактов API (в т.ч. приведение Security к `[ApiController]`/ProblemDetails); генерация типов из OpenAPI (§4.4 — как кандидат на потом); смена схемы хранения токена; i18n; SSR; перенос SPA в общий monorepo-тулинг с бэкендом.
