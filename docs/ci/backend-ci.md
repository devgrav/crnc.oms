# CI бэкенда: `.github/workflows/backend-ci.yml`

## Контекст

До этого момента в репозитории не было ни одного CI-конфига: ни `.github/`, ни
`azure-pipelines.yml`, ничего. Четыре контекста мигрировали на .NET 10 и обросли
e2e-наборами (issue #1–#8), но проверялись только руками. [Issue #10](https://github.com/devgrav/crnc.oms/issues/10)
закрывает этот пробел: сборка .NET, юнит-тесты и API e2e-тесты для каждого проекта,
с заделом под CD, который будет собирать отдельный Docker-образ на каждый микросервис.

Главный вопрос, который issue ставит явно, — стратегия для монорепозитория: собирать
всё на каждый коммит или только затронутое. Выбран второй вариант: e2e-наборы поднимают
настоящие контейнеры и собирают настоящие образы сервисов, это самая дорогая часть
пайплайна, и гонять её ради правки в соседнем контексте смысла нет.

## Согласованные решения

1. **Фильтрация по путям.** Каждый ограниченный контекст целиком лежит в
   `src/Server/src/Crnc.Oms.<Context>/`, и **ни одной `ProjectReference` через эту границу
   нет** (проверено). Значит «какие контексты изменились» — чисто вопрос путей, анализ
   графа сборки не нужен.
2. **Сборка по контекстным `.sln`, а не по `src/Server/Crnc.Oms.sln`.** Корневое решение
   **не является надмножеством**: в нём лежит только один e2e-проект из четырёх
   (`Crnc.Oms.Security.E2ETests`), а Sales/Production/Notification отсутствуют. `dotnet test`
   по нему молча пропустил бы три набора из четырёх. Контекстные решения — то, что
   соответствует Docker-сборкам (см. AGENTS.md, «Commands»).
3. **Матрица по контекстам, а не по проектам.** Имена путей регулярны — `sln`, юнит-тесты
   и e2e-проект выводятся из одного имени контекста (`Security`, `Sales`, `Production`,
   `Notification`), поэтому все четыре джобы описаны одним набором шагов.
4. **Юнит-тесты подхватываются по конвенции.** Шаг запускает
   `Crnc.Oms.<Context>.Tests/Crnc.Oms.<Context>.Tests.csproj`, **если файл существует**.
   Сегодня он есть только у Sales; AGENTS.md ожидает, что остальные его заведут, — тогда
   правка workflow не понадобится.
5. **Сборка и e2e разведены по разным джобам.** Ошибка компиляции краснеет за пару минут,
   не дожидаясь двадцати минут контейнеров. Повторная сборка в e2e-джобе дешёвая: там
   `dotnet test` идёт по одному e2e-`csproj`, а не по всему решению (у Security, Sales и
   Notification e2e-проекты вообще без `ProjectReference`).
6. **Сводная джоба `backend-ci` как единственный required-чек.** Матричные джобы условные:
   на PR, который трогает только `src/Client` или `docs/`, они пропускаются. Требовать их
   напрямую в branch protection нельзя — такой PR завис бы навсегда. Джоба с `if: always()`
   проверяет результаты (`success` и `skipped` — ок, остальное — красный) и даёт одно
   стабильное имя чека.
7. **Никаких сторонних actions.** Только `actions/checkout`, `setup-dotnet`, `cache`,
   `upload-artifact`. Детектор изменений — двадцать строк bash вместо `dorny/paths-filter`:
   меньше поверхность зависимостей и видно, что именно он делает.
8. **Workflow не ограничен `paths:` на уровне `on:`.** Иначе для клиентских PR чек
   `Backend CI` не появлялся бы вовсе, и branch protection не смог бы его дождаться.
   Вместо этого workflow запускается всегда, а матрица схлопывается в пустую.

## Как устроен пайплайн

```
changes ──┬── build (матрица: изменённые контексты) ──┬── e2e (та же матрица) ──┐
          │                                           │                         │
          └───────────────────────────────────────────┴─────────────────────────┴── backend-ci
```

### `changes`

Считает список контекстов и отдаёт его JSON-массивом в `outputs.contexts`, который
разворачивается через `fromJSON` в `strategy.matrix.context`.

База для диффа:

| Событие | База |
|---|---|
| `pull_request` | `github.event.pull_request.base.sha` (HEAD — merge-коммит, так что дифф = ровно изменения PR) |
| `push` | `github.event.before` |
| `workflow_dispatch` | нет — собираются все контексты |

Если база пустая, нулевая (`000…0`, новая ветка) или не резолвится в коммит — собираются
все четыре контекста. Правка самого `backend-ci.yml` тоже включает полную сборку: пайплайн
надо прогнать против всего, чем он управляет.

Порядок в матрице фиксированный (`Security, Sales, Production, Notification`), потому что
скрипт идёт по литеральному списку, а не по порядку файлов в диффе.

### `build`

`dotnet restore` → `dotnet build -c Release --no-restore` по контекстному `.sln` →
юнит-тесты, если проект существует. Кэш NuGet — `~/.nuget/packages` по хэшу всех
`src/Server/**/*.csproj`.

Сборка решения компилирует и e2e-проект тоже (он член `.sln` во всех четырёх контекстах),
так что ошибка компиляции в тестах ловится здесь, а не через двадцать минут.

### `e2e`

`dotnet test` по `Crnc.Oms.<Context>.E2ETests`. Что важно знать:

- **`DOCKER_HOST` здесь намеренно не выставляется.** `tcp://localhost:2375` из AGENTS.md —
  костыль под Windows и Docker Desktop. На Linux-раннере Testcontainers находит сокет сам.
- **Фикстуры переносимы как есть.** Все проброшенные порты объявлены как
  `WithPortBinding(port, true)` (случайный хост-порт), а обращения идут через
  `container.Hostname` и `GetMappedPublicPort(...)`. Фиксированных хост-портов и имён
  контейнеров нет, конфликтовать нечему.
- **Базовые образы .NET пред-подтягиваются отдельным шагом**, чтобы их скачивание не
  съедало таймауты готовности внутри фикстуры (`WithTimeout(TimeSpan.FromMinutes(3))`).
- Каждая фикстура **собирает образ сервиса из его настоящего `Dockerfile`** через
  `ImageFromDockerfileBuilder`. Кэш слоёв Docker между запусками не переносится — это
  и есть основная стоимость джобы. `timeout-minutes: 45` взят с запасом; дороже всех
  Notification, который поднимает три деплой-юнита сразу.

### Артефакты

TRX-отчёты обоих видов тестов выкладываются как артефакты (`unit-test-results-<Context>`,
`e2e-test-results-<Context>`) с `if: always()`, чтобы упавший прогон можно было разобрать
не по логам.

## Что осталось за рамками

- **Фронтенд.** Issue #10 — про бэкенд; SPA живёт в issue #9 (миграция на современный стек).
  Детектор изменений про `src/Client` знает ровно одно: это не бэкенд-контекст.
- **CD и публикация образов.** Сегодня ни один образ не тегируется и никуда не пушится, в
  `docker-compose.yml` нет ни одного ключа `image:` — схемы именования в реестре просто не
  существует. Когда дойдут руки, отправной точкой будет то же самое `outputs.contexts`:
  матрица деплой-юнитов (их семь, а не четыре — Notification ships as Email, Push, Gateway
  и Push.Client), `docker buildx` с кэшем в GHA и push в GHCR.
- **`Crnc.Oms.Notification.Push.Client` не собирается в образ ни на одном шаге CI.** Его
  `.csproj` компилируется в составе `Crnc.Oms.Notification.sln`, но `Dockerfile` не трогает
  никто: e2e-фикстура Notification поднимает Email, Push и Gateway, а роль push-клиента
  играет SignalR-клиент внутри тестового процесса. Закроется вместе с CD-матрицей образов.
- **Покрытие кода.** `coverlet.collector` есть во всех тестовых проектах, но не включён —
  отдельное решение, не смешиваем с заведением пайплайна.
